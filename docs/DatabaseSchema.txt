ConfigTrace Database Schema
Internal Document — May 2026


OVERVIEW

This document defines the PostgreSQL database schema for the ConfigTrace MVP. The schema is designed for use with SQLAlchemy ORM models, Alembic migrations, and a FastAPI backend. It covers the seven core tables required to support user accounts, Cloudflare integrations, DNS resource tracking, point-in-time snapshots, diff-based change records, alert events, and sync run history.

The schema is deliberately practical. It favors simplicity and correctness over premature optimization, uses JSONB for configuration state to avoid rigid normalization of provider-specific fields, and is designed to extend to new providers without structural migrations. Every table in this document corresponds directly to a SQLAlchemy model and an Alembic migration step.


GUIDING DESIGN PRINCIPLES

Snapshots are immutable. Once a snapshot is written, it is never updated or deleted. All history is preserved. This is what makes ConfigTrace trustworthy as a diagnosis tool.

Changes are derived and stored. The diff between two snapshots is computed once by the diff service and written to the changes table. Timeline queries read from this table directly; they do not recompute diffs at read time. This keeps the dashboard fast under load.

JSONB for configuration state. Each provider returns configuration in a different shape. Storing the normalized state as JSONB means new providers and new fields can be added without schema migrations. The diff service compares JSONB documents in application code, not in SQL.

Content hashing for efficiency. Each snapshot stores a SHA-256 hash of its serialized state. The snapshot service compares the new hash to the most recent snapshot hash before writing. If hashes match, no snapshot is written and no diff is run. This avoids unnecessary writes on no-change syncs.

Row-level scoping by user. Every entity in the schema ultimately belongs to a user. All queries are scoped by user ID. This is the foundation for multi-tenant readiness in Phase 8 when the schema is extended with organizations.

Encryption outside the database. Integration credentials are encrypted at the application layer before being written to the integrations table. The database stores only ciphertext. The encryption key lives in the server environment, not in the schema.


TABLE 1: USERS

Purpose

The users table stores one record per authenticated user. It is created on first login via Clerk. All other entities in the system are scoped to a user through foreign keys that trace back to this table. In the MVP, ConfigTrace is single-user. In Phase 8, this table will be extended with organization membership.

Fields

    id                  UUID, primary key, default gen_random_uuid()
    clerk_id            TEXT, not null, unique
    email               TEXT, not null
    display_name        TEXT, nullable
    created_at          TIMESTAMPTZ, not null, default now()
    updated_at          TIMESTAMPTZ, not null, default now()

Field Notes

The id field is a UUID generated by PostgreSQL using gen_random_uuid(). Using UUIDs rather than sequential integers prevents enumeration attacks and makes IDs safe to expose in API responses and URLs.

The clerk_id field is the immutable external identifier assigned by Clerk to the user. It is the primary lookup key used when validating a JWT from the frontend. It is marked unique to enforce one-to-one mapping between Clerk accounts and ConfigTrace user records.

The email and display_name fields are stored for reference and UI display. They are not used for authentication.

Primary Key

    id (UUID)

Indexes

    UNIQUE index on clerk_id for fast JWT-to-user resolution on every authenticated request.

Foreign Keys

    None. The users table is the root of the ownership hierarchy.

Why This Table Exists

Every query in the system is scoped to an authenticated user. Without a resolved internal user ID, row-level access control cannot be enforced. The users table provides this anchor. It is the first record created in the system and the last one that should ever be deleted.


TABLE 2: INTEGRATIONS

Purpose

The integrations table stores one record per connected provider account. An integration represents the connection between ConfigTrace and an external system, in the MVP, a Cloudflare account. It stores the encrypted API credentials, the provider identifier, the current status of the connection, and timestamps for creation and last sync. Every resource, snapshot, and change traces back to an integration.

Fields

    id                          UUID, primary key, default gen_random_uuid()
    user_id                     UUID, not null, foreign key to users.id
    provider                    TEXT, not null
    display_name                TEXT, not null
    encrypted_credentials       BYTEA, not null
    credential_iv               BYTEA, not null
    status                      TEXT, not null, default 'active'
    last_synced_at              TIMESTAMPTZ, nullable
    scheduled_sync_enabled      BOOLEAN, not null, default false
    sync_interval_minutes       INTEGER, nullable
    created_at                  TIMESTAMPTZ, not null, default now()
    updated_at                  TIMESTAMPTZ, not null, default now()

Field Notes

The provider field stores a short string identifier for the provider. In the MVP this is always 'cloudflare'. In later phases it will be 'stripe', 'github', and so on. This field drives which connector module the sync orchestration task instantiates.

The encrypted_credentials field stores the AES-GCM ciphertext of the serialized credentials object. For Cloudflare, the credentials object contains the API token and zone ID. The serialization format is JSON, encrypted with a symmetric key from the server environment. The application layer is responsible for encryption and decryption; the database stores only the ciphertext bytes.

The credential_iv field stores the initialization vector used during AES-GCM encryption. It must be stored alongside the ciphertext to enable decryption. The IV is unique per encryption operation and is not secret, but it must be stored correctly or decryption will fail.

The status field uses a TEXT column with application-level validation rather than a PostgreSQL enum. Valid values are 'active', 'paused', and 'error'. Using TEXT rather than an enum avoids the overhead of a migration when new status values are needed. The FastAPI layer enforces valid values with a Pydantic enum.

The last_synced_at field is updated by the Celery worker on every successful sync completion. It is used by the integrations page to show when the integration was last successfully polled.

The scheduled_sync_enabled and sync_interval_minutes fields are reserved for Phase 4. They are included in the initial migration so Phase 4 requires only a backfill migration rather than a structural one.

Primary Key

    id (UUID)

Foreign Keys

    user_id references users.id on delete cascade

Indexes

    Index on user_id for fast lookup of all integrations belonging to a user.
    Index on (user_id, status) for filtering active integrations when scheduling background syncs.

Why This Table Exists

The integrations table is the registry of what external systems ConfigTrace is monitoring for a given user. Every sync task starts here: it loads credentials from this table, instantiates the appropriate connector, and updates this table with the sync result. Without integrations, there is nothing to sync and no resources to track.


TABLE 3: RESOURCES

Purpose

The resources table stores one record per monitored resource within an integration. For Cloudflare, a resource is a DNS zone. A single integration may contain multiple zones, each tracked independently. Resources are the unit of granularity at which snapshots are stored and diffs are computed. All snapshot and change records are linked to a resource, not directly to an integration.

Fields

    id                          UUID, primary key, default gen_random_uuid()
    integration_id              UUID, not null, foreign key to integrations.id
    user_id                     UUID, not null, foreign key to users.id
    provider_resource_type      TEXT, not null
    provider_resource_id        TEXT, not null
    display_name                TEXT, not null
    metadata                    JSONB, nullable
    last_snapshot_at            TIMESTAMPTZ, nullable
    is_active                   BOOLEAN, not null, default true
    created_at                  TIMESTAMPTZ, not null, default now()
    updated_at                  TIMESTAMPTZ, not null, default now()

Field Notes

The provider_resource_type field identifies what kind of resource this is within the provider's model. For Cloudflare DNS, this value is 'cloudflare_dns_zone'. For Stripe this will be 'stripe_webhook_endpoints', and for GitHub it will be 'github_repo_branch_protection'. This string is used by the diff and risk services to apply the correct comparison logic and rule set.

The provider_resource_id field stores the provider's native identifier for this resource. For Cloudflare zones, this is the Cloudflare zone ID. This field is used to match a resource record to the correct provider entity when constructing connector requests.

The metadata field is a JSONB column for provider-specific resource attributes that do not fit into the normalized fields but are useful for display or filtering. For a Cloudflare zone, this might store the zone name, plan level, or account ID. This field is informational and not used for diff computation.

The is_active field supports soft deletion. When a resource is deactivated, its snapshots and changes are preserved but it is excluded from new sync runs. This is set to false when a zone is removed from the integration or the integration is deactivated. It is not the same as a hard delete.

The user_id field is denormalized from integrations to allow direct user-scoped queries on the resources table without a join. This is an intentional tradeoff: a small amount of write redundancy in exchange for simpler and faster read queries.

Primary Key

    id (UUID)

Foreign Keys

    integration_id references integrations.id on delete cascade
    user_id references users.id on delete cascade

Indexes

    Index on integration_id for fast lookup of all resources under an integration.
    Index on user_id for user-scoped resource queries.
    Unique index on (integration_id, provider_resource_id) to prevent duplicate resource records for the same provider entity under the same integration.

Why This Table Exists

Snapshots and diffs operate at the resource level. A Cloudflare integration may contain five DNS zones, each of which must be snapshotted and diffed independently. The resources table is what allows the system to track each zone's configuration history separately. Without this table, all state for an integration would be collapsed into a single snapshot, making it impossible to isolate changes to a specific zone.


TABLE 4: SNAPSHOTS

Purpose

The snapshots table stores one record per point-in-time snapshot of a resource's configuration state. Snapshots are the foundation of everything ConfigTrace does. Diffs are computed by comparing two snapshots. History is read from snapshots. Risk is derived from diffs, which come from snapshots. Snapshots are never modified or deleted after creation.

Fields

    id                  UUID, primary key, default gen_random_uuid()
    resource_id         UUID, not null, foreign key to resources.id
    integration_id      UUID, not null, foreign key to integrations.id
    user_id             UUID, not null, foreign key to users.id
    state               JSONB, not null
    content_hash        TEXT, not null
    triggered_by        TEXT, not null
    sync_run_id         UUID, nullable, foreign key to sync_runs.id
    created_at          TIMESTAMPTZ, not null, default now()

Field Notes

The state field stores the full normalized configuration state returned by the connector as a JSONB document. For Cloudflare DNS, this is a JSON array of DNS record objects, each containing id, type, name, content, ttl, proxied, priority, comment, and modified_on fields. The structure of this JSONB document is defined by the connector's normalization logic, not by the database schema.

The content_hash field stores a SHA-256 hex digest of the canonical serialization of the state field. The snapshot service computes this hash before writing. If the hash matches the most recent snapshot for this resource, the write is skipped and no new snapshot record is created. This prevents the database from accumulating duplicate rows during no-change syncs.

The triggered_by field records what initiated this sync. Valid values are 'manual' and 'scheduled'. In the MVP, this is always 'manual'. This field is used in the timeline to distinguish sync types and in Phase 4 to filter sync history.

The sync_run_id field links the snapshot to the sync run that produced it. This is nullable in the MVP because sync_runs is introduced in Phase 4. In Phase 4 this column will be backfilled for new snapshots. The foreign key is deferred to avoid a circular dependency during initial migration.

The integration_id and user_id fields are denormalized from the resource to support direct filtered queries on the snapshots table without joins. This matters for the timeline and resource history queries, which are the most frequently executed read paths in the application.

Primary Key

    id (UUID)

Foreign Keys

    resource_id references resources.id on delete restrict
    integration_id references integrations.id on delete restrict
    user_id references users.id on delete restrict
    sync_run_id references sync_runs.id on delete set null (nullable, Phase 4)

Deletion behavior uses restrict rather than cascade on resource and integration foreign keys. Snapshots should not be automatically deleted when a resource is deactivated. They form the historical record and must be preserved.

Indexes

    Index on (resource_id, created_at DESC) for the diff service, which always needs the two most recent snapshots for a resource.
    Index on (integration_id, created_at DESC) for the resource history page and integration-level timeline queries.
    Index on (user_id, created_at DESC) for user-scoped history queries.
    Index on content_hash for the deduplication check before each snapshot write.
    GIN index on state for potential full-text search added in Phase 2.

Why This Table Exists

Snapshots are the raw material from which everything else is derived. Without snapshots, there is no history, no diff, and no change record. The snapshot table must be correct, complete, and immutable. It is the most critical table in the schema. If a snapshot is missing or corrupted, ConfigTrace will produce incorrect diffs. If snapshots are deleted, historical comparison is permanently broken.


TABLE 5: CHANGES

Purpose

The changes table stores one record per detected change between two consecutive snapshots of a resource. Each row represents a single meaningful difference: a DNS record that was added, a record that was deleted, or a specific field on a record that was modified. Changes are the primary data shown in the timeline and the change detail view. They are written once by the diff service and never updated.

Fields

    id                      UUID, primary key, default gen_random_uuid()
    resource_id             UUID, not null, foreign key to resources.id
    integration_id          UUID, not null, foreign key to integrations.id
    user_id                 UUID, not null, foreign key to users.id
    prev_snapshot_id        UUID, not null, foreign key to snapshots.id
    new_snapshot_id         UUID, not null, foreign key to snapshots.id
    change_type             TEXT, not null
    record_identifier       TEXT, not null
    field_path              TEXT, nullable
    prev_value              JSONB, nullable
    new_value               JSONB, nullable
    risk_level              TEXT, not null
    risk_reason             TEXT, nullable
    provider_metadata       JSONB, nullable
    created_at              TIMESTAMPTZ, not null, default now()

Field Notes

The change_type field identifies the nature of the change. Valid values are 'added', 'removed', and 'modified'. For 'added' changes, prev_value is null. For 'removed' changes, new_value is null. For 'modified' changes, both prev_value and new_value are set.

The record_identifier field stores a human-readable stable identifier for the affected entity. For DNS changes, this is typically the Cloudflare record ID, supplemented by the record type and name for display purposes, for example 'A record: api.example.com'. This field is used in the timeline to label each change row without requiring a join back to the snapshot state.

The field_path field applies to 'modified' changes. It stores the dot-notation path to the specific field that changed within a record, such as 'content', 'ttl', or 'proxied'. For 'added' and 'removed' changes, field_path is null because the change applies to the whole record, not a single field. The diff service may produce multiple change rows for a single modified record if more than one field changed.

The prev_value and new_value fields store JSONB representations of the before and after state for the affected field or record. For a field-level modification, these are scalar values wrapped in JSONB for type safety, for example the number 3600 or the string "192.0.2.1". For added and removed records, these store the full record object. Storing values as JSONB rather than TEXT preserves type information and allows structured rendering in the frontend.

The risk_level field stores the classification assigned by the risk service. Valid values are 'low', 'medium', 'high', and 'critical'. This is set at write time and is never recomputed unless the risk rules are backfilled explicitly.

The risk_reason field stores a short plain-text explanation of why the risk level was assigned. This is displayed in the change detail view. For example: "TTL reduced to 60 seconds or below on a proxied record. Accelerates global propagation and reduces rollback window." Risk reasons are generated by the risk service at classification time.

The provider_metadata field stores any additional provider-specific context about the change that does not fit into the normalized fields. For Cloudflare, this might include the zone name, zone ID, account ID, or the full before and after Cloudflare record objects. This field is nullable and informational.

Primary Key

    id (UUID)

Foreign Keys

    resource_id references resources.id on delete restrict
    integration_id references integrations.id on delete restrict
    user_id references users.id on delete restrict
    prev_snapshot_id references snapshots.id on delete restrict
    new_snapshot_id references snapshots.id on delete restrict

All foreign keys use restrict rather than cascade. Changes must not be automatically deleted when a snapshot or resource is deactivated. They are the primary historical record surfaced in the UI.

Indexes

    Index on (user_id, created_at DESC) for the main timeline query.
    Index on (resource_id, created_at DESC) for the resource history view.
    Index on (integration_id, created_at DESC) for integration-scoped timeline filtering.
    Index on (risk_level, created_at DESC) for filtering by risk level in the timeline.
    Index on (user_id, risk_level, created_at DESC) for the combined user-scoped risk-filtered timeline query, which is the most common dashboard query pattern.

Why This Table Exists

The timeline is the core interface of ConfigTrace. Every row in the timeline corresponds to one row in the changes table. Storing changes as pre-computed records means the timeline query is a simple indexed SELECT with ORDER BY and WHERE filters. Without this table, every timeline load would require re-running the diff service against snapshot pairs, which would be slow and expensive. The changes table is the materialized output of the diff and risk pipeline.


TABLE 6: ALERTS

Purpose

The alerts table stores one record per alert event dispatched by the alerting system. Each row records which change triggered the alert, what channel it was sent to, the delivery status, and timestamps for creation and delivery. The table provides an audit trail of all notifications and allows the UI to show which changes have generated alerts. This table is created in the MVP schema as a placeholder. Alert dispatch logic is implemented in Phase 3.

Fields

    id                      UUID, primary key, default gen_random_uuid()
    change_id               UUID, not null, foreign key to changes.id
    user_id                 UUID, not null, foreign key to users.id
    integration_id          UUID, not null, foreign key to integrations.id
    alert_config_id         UUID, nullable
    channel                 TEXT, not null
    destination             TEXT, not null
    payload                 JSONB, nullable
    status                  TEXT, not null, default 'pending'
    error_message           TEXT, nullable
    retry_count             INTEGER, not null, default 0
    created_at              TIMESTAMPTZ, not null, default now()
    delivered_at            TIMESTAMPTZ, nullable

Field Notes

The channel field identifies the notification channel. In Phase 3, the only valid value is 'slack'. Future phases may add 'email', 'pagerduty', or 'webhook'. Using TEXT rather than an enum keeps the schema flexible.

The destination field stores the specific delivery address for the channel. For Slack, this is the webhook URL. For email, this would be the recipient address. This value is copied from the alert configuration at dispatch time, not looked up dynamically, so the audit trail is accurate even if the alert configuration is later changed.

The payload field stores the full message payload sent to the destination, serialized as JSONB. This allows the alert history view to show exactly what was sent and supports debugging of failed deliveries.

The status field tracks the delivery lifecycle. Valid values are 'pending', 'delivered', and 'failed'. The Celery dispatch task updates this field after each attempt.

The error_message field stores the HTTP status code, error body, or exception message from a failed delivery attempt. This is used in the alert history view and by the retry logic to distinguish permanent failures from transient ones.

The retry_count field tracks how many delivery attempts have been made. The dispatch task increments this on each attempt. After three attempts, the status is set to 'failed' regardless of the error type.

The alert_config_id field is nullable because the alert configuration table (alert_configs) is not created until Phase 3. The column is present in the schema from the start to avoid a structural migration in Phase 3. In Phase 3, this will reference the alert_configs table.

Primary Key

    id (UUID)

Foreign Keys

    change_id references changes.id on delete restrict
    user_id references users.id on delete restrict
    integration_id references integrations.id on delete restrict

Indexes

    Index on (user_id, created_at DESC) for the alert history view.
    Index on (change_id) for the timeline badge lookup that shows whether a change has triggered an alert.
    Index on (status, created_at DESC) for the retry worker to find pending or failed alerts.

Why This Table Exists

The alerting system needs an audit trail. Without this table, there is no way to answer questions like: was the engineer notified about this critical change? How many times did the alert retry before failing? Which changes have already been alerted on? The table also prevents duplicate alert dispatch: the Celery task checks for an existing alert record for a change_id before creating a new one.


TABLE 7: SYNC_RUNS

Purpose

The sync_runs table stores one record per sync execution. It tracks the trigger type, start and end times, outcome, and change count for every sync that has been run. In the MVP, this table is created but used minimally. Its full implementation is the primary backend task of Phase 4. It is included in the initial schema because the snapshots table references it via sync_run_id and because having the table present from the start avoids a structural dependency in Phase 4.

Fields

    id                      UUID, primary key, default gen_random_uuid()
    integration_id          UUID, not null, foreign key to integrations.id
    user_id                 UUID, not null, foreign key to users.id
    triggered_by            TEXT, not null
    status                  TEXT, not null, default 'pending'
    started_at              TIMESTAMPTZ, not null, default now()
    completed_at            TIMESTAMPTZ, nullable
    change_count            INTEGER, nullable
    snapshot_count          INTEGER, nullable
    error_message           TEXT, nullable
    created_at              TIMESTAMPTZ, not null, default now()

Field Notes

The triggered_by field stores the sync trigger type. Valid values are 'manual' and 'scheduled'. In the MVP all syncs are manual. Phase 4 adds 'scheduled' when Celery Beat is activated.

The status field tracks the sync lifecycle. Valid values are 'pending', 'running', 'completed', and 'failed'. The Celery worker updates status to 'running' when it starts the task, to 'completed' when it finishes successfully, and to 'failed' if an unrecoverable error occurs.

The change_count field records how many change records were written during this sync. A value of zero means the sync completed successfully but the configuration had not changed since the last snapshot. This is a normal and expected outcome for many syncs.

The snapshot_count field records how many new snapshots were written during this sync. This is typically equal to the number of resources under the integration, unless content hashing caused some resources to be skipped due to no state change.

The error_message field stores the exception message or error context if the sync failed. This is used in the sync history view and for debugging failed background tasks.

Primary Key

    id (UUID)

Foreign Keys

    integration_id references integrations.id on delete cascade
    user_id references users.id on delete cascade

Indexes

    Index on (integration_id, started_at DESC) for the sync history view, which paginates syncs for a specific integration in reverse chronological order.
    Index on (user_id, started_at DESC) for user-scoped sync history.
    Index on (status, started_at) for the scheduled sync task, which needs to detect if a previous sync is still running before enqueuing a new one.

Why This Table Exists

Without sync run records, there is no history of when syncs ran, how long they took, or whether they succeeded. The sync history view, the last synced timestamp on the integrations page, and the logic that prevents concurrent syncs from running all depend on this table. It is also the parent record for all snapshots produced in a sync, which allows the resource history view to group snapshots by sync event.


SCHEMA DESIGN TRADEOFFS

Storing Snapshot State as JSONB vs Normalized Fields

The state column in the snapshots table stores the full normalized configuration state as a JSONB document rather than as rows in a normalized relational table. This is an intentional and important tradeoff.

The argument for normalization is that relational structure enables efficient SQL queries over individual fields. If DNS record content values were stored in their own column, you could query SELECT content FROM dns_records WHERE zone_id = X directly.

The argument for JSONB is that normalization ties the schema tightly to a single provider's data model. Every new provider would require a new table or a shared EAV table that is difficult to query and maintain. JSONB allows the snapshot service and diff service to be provider-agnostic. The connector normalizes provider state into an internal format, and the snapshot service stores that format without caring what it contains. The diff service compares two JSONB documents in application code. This architecture is what makes adding Stripe, GitHub, or any other provider a matter of writing a new connector module rather than a new table.

The practical consequence is that you cannot write a SQL query to find all snapshots where a specific DNS record's content field equals a specific IP address without using PostgreSQL's JSONB path operators, which are more complex than standard SQL. For the ConfigTrace use case, this is an acceptable tradeoff. The primary read pattern is by resource and timestamp, not by field value, and complex queries over snapshot content are not in the MVP scope.

Hashing Snapshots for Deduplication

The content_hash field on the snapshots table enables the snapshot service to skip writing a new snapshot when the configuration has not changed. Without this optimization, every sync would write a new snapshot row and trigger a diff computation even on no-change syncs. For integrations that sync frequently, this would cause rapid database growth and unnecessary diff computation.

The hash is computed as SHA-256 of the canonical JSON serialization of the normalized state. Canonical serialization means keys are sorted and the output is deterministic regardless of the order in which the provider API returned records. The content of the hash must match the content of the JSONB state field exactly, or the deduplication check will produce false negatives.

One risk with hash-based deduplication is hash collisions. SHA-256 collisions are cryptographically impractical, so this is not a real concern in practice. A more realistic risk is a bug in the serialization logic that produces the same hash for genuinely different states. This would cause ConfigTrace to miss real changes. The serialization function must be tested carefully with known inputs and outputs.

Handling Deleted Resources

When a DNS record is deleted in Cloudflare, it disappears from the next snapshot. The diff service detects this as a 'removed' change and writes a change record with the full previous record state and a null new value. The resource itself in the resources table is not deleted. The is_active flag is set to false only when the entire zone or integration is deactivated, not when individual records within a zone are removed.

This distinction matters: a zone can remain active even after records are deleted from it. The changes table preserves the history of those deletions. The resource record is the container for snapshot history; it should not be deleted or deactivated just because some of its contents changed.

When an integration is deleted by the user, the is_active flag on the integration is set to false and related resources are also flagged inactive. The snapshots and changes rows are preserved under a restrict foreign key constraint. They cannot be deleted without explicitly removing the changes and snapshots first. This is the correct behavior: historical data should survive integration deactivation.

Tracking Sync Status

The sync_runs table tracks the status of each sync execution through a lifecycle: pending, running, completed, and failed. The Celery worker is responsible for updating this status at each stage of execution. There is no transaction-level guarantee that the status update will be written if the worker process crashes mid-sync.

To handle worker crashes, the sync orchestration logic should check for sync_runs records that have been in 'running' status for longer than a configurable timeout (for example, five minutes) and mark them as 'failed'. This check can run at the start of each sync task before processing begins. It prevents orphaned running records from accumulating and blocking the scheduled sync logic that checks for concurrent runs.

Tracking Provider-Specific Metadata

The resources.metadata, changes.provider_metadata, and snapshots fields all provide space for provider-specific information that does not fit into the normalized schema. These JSONB columns serve as escape hatches for data that is useful for display or debugging but does not need to be queried directly.

The rule for what goes in these columns versus the normalized fields is: if the application code needs to query or filter on a value, it belongs in a dedicated column with an index. If the value is only needed for display, for raw data export, or as context for debugging, it belongs in the JSONB metadata column. Applying this rule consistently prevents the normalized fields from accumulating provider-specific columns that only apply to one integration type.

Multi-Tenant Readiness

The current schema is single-tenant: every table has a user_id column and all queries are scoped by user. The Phase 8 roadmap adds an organizations table and migrates ownership from users to organizations.

The transition from user-level to organization-level ownership requires adding an organization_id column to users, integrations, resources, snapshots, changes, and alerts, updating all query scopes to use organization_id, and enforcing role-based access at the API layer. Because the current schema consistently uses user_id as the scoping column, this migration is mechanical: add the organization_id column, backfill it from the user's organization membership, update the query layer, and add the role check middleware.

The JSONB columns in the schema do not complicate this migration because they do not contain ownership identifiers. All scoping is in the normalized columns.


ALEMBIC MIGRATION ORDER

Migrations must be applied in the following dependency order to satisfy foreign key constraints:

    1. users
    2. integrations (depends on users)
    3. resources (depends on integrations, users)
    4. sync_runs (depends on integrations, users)
    5. snapshots (depends on resources, integrations, users, sync_runs)
    6. changes (depends on snapshots, resources, integrations, users)
    7. alerts (depends on changes, users, integrations)

Each migration should be reversible with a corresponding downgrade function. The initial migration for Phase 0 creates all seven tables in a single Alembic revision. Phase 4 adds the scheduled_sync_enabled and sync_interval_minutes columns to integrations and activates the sync_run_id foreign key on snapshots. Phase 3 adds the alert_configs table and populates the alert_config_id column on alerts.


SQLALCHEMY MODEL NOTES

All models should inherit from a shared declarative base. The following conventions apply across all models:

    id fields use the UUID type from sqlalchemy.dialects.postgresql and default to text(gen_random_uuid()) at the database level.
    JSONB fields use the JSONB type from sqlalchemy.dialects.postgresql.
    TIMESTAMPTZ fields use DateTime(timezone=True).
    All models include created_at and updated_at columns. The updated_at column should be set automatically using a SQLAlchemy event listener or an onupdate trigger.
    Soft-delete fields (is_active on resources) are BOOLEAN columns, not nullable deletion timestamps. This keeps query filters simple: WHERE is_active = true.

The relationship between integrations and resources should be defined as a SQLAlchemy relationship with lazy loading disabled for the primary query paths. The sync orchestration task loads the integration and its resources in a single query before dispatching connector work.


INDEX SUMMARY

This section consolidates the indexes defined across all tables for use in the initial Alembic migration.

users:
    UNIQUE on clerk_id

integrations:
    Index on user_id
    Index on (user_id, status)

resources:
    Index on integration_id
    Index on user_id
    UNIQUE on (integration_id, provider_resource_id)

snapshots:
    Index on (resource_id, created_at DESC)

    Index on (user_id, created_at DESC)
    Index on content_hash
    GIN index on state

    Index on (integration_id, created_at DESC)
    Index on (risk_level, created_at DESC)
    Index on (user_id, risk_level, created_at DESC)
