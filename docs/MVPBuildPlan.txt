ConfigTrace MVP Build Plan
Internal Document - May 2026


PURPOSE

This document is the ground-level engineering execution plan for the ConfigTrace Cloudflare DNS monitoring MVP. It is written for a solo founder-engineer building milestone by milestone. Each milestone has a clear goal, specific files to create, backend and frontend tasks, a test criterion, and a definition of done. Do not start a new milestone until the current one is done. Do not implement future-phase features inside MVP milestones.

The completed MVP must prove four things: the snapshot and diff engine works reliably, the risk classification is meaningful, the timeline is useful for incident diagnosis, and engineers will trust the product enough to connect a real system to it.

MILESTONE 6: CLOUDFLARE CONNECTOR

Goal

The Cloudflare connector is a self-contained Python module that accepts an API token and zone ID, calls the Cloudflare Zones API, handles pagination and rate limit backoff, and returns a normalized list of DNS record objects in ConfigTrace's internal format. The connector has no knowledge of snapshots, diffs, or risk. It is a pure fetch-and-normalize function.

Files to Create

    /backend/app/connectors/__init__.py          connector package
    /backend/app/connectors/base.py              BaseConnector protocol/abstract class
    /backend/app/connectors/cloudflare.py        CloudflareConnector implementation
    /backend/app/connectors/cloudflare_schema.py normalized DNS record dataclass or TypedDict

Backend Tasks

    In base.py, define a BaseConnector abstract class with one required method: fetch(credentials: dict) -> list[dict]. All connectors must implement this interface. The return type is a list of normalized record dictionaries.
    In cloudflare_schema.py, define a CloudflareDNSRecord TypedDict or dataclass with fields: record_id (str), record_type (str), name (str), content (str), ttl (int), proxied (bool), priority (int or None), comment (str or None), modified_on (str). This is ConfigTrace's internal normalized format for a DNS record.
    In cloudflare.py, implement CloudflareConnector(BaseConnector).
        The fetch method accepts a credentials dict with api_token and zone_id keys.
        Call GET https://api.cloudflare.com/client/v4/zones/{zone_id}/dns_records with the Authorization: Bearer {api_token} header.
        Handle pagination: the Cloudflare API returns a result_info object with page, per_page, and total_count. Loop through pages until all records are retrieved.
        Implement rate limit backoff: on a 429 response, read the Retry-After header and sleep for that duration before retrying. Maximum three retries.
        On a 401 or 403 response, raise an AuthenticationError with a clear message.
        On any other non-200 response, raise a ConnectorError with the status code and response body.
        Normalize each raw Cloudflare DNS record object into a CloudflareDNSRecord. Map Cloudflare's id field to record_id. Map type to record_type. Map all other fields directly.
        Return a list of CloudflareDNSRecord objects serialized to plain dicts.
    Write a standalone validate_token function that takes an api_token and zone_id, makes a single HEAD or GET call to verify the token has DNS read access to that zone, and returns True or raises an AuthenticationError. This is used during integration setup to reject bad tokens before saving.

Test Criteria

    With a valid Cloudflare API token and zone ID pointing at a real or test zone, fetch() returns a non-empty list of normalized DNS record dicts.
    Each returned dict contains record_id, record_type, name, content, ttl, and proxied keys.
    With an invalid token, fetch() raises AuthenticationError.
    With a nonexistent zone ID and valid token, fetch() raises ConnectorError.
    validate_token() returns True for a valid credential pair and raises AuthenticationError for an invalid token.
    The connector correctly pages through zones with more than 100 records (Cloudflare's default page size).

Definition of Done

The Cloudflare connector can be imported and called standalone, without any database, without any Celery task, and without any other application code. It is a pure function. Calling it with valid credentials returns the right data. Calling it with invalid credentials raises the right errors.


MILESTONE 7: MANUAL SYNC ENDPOINT

Goal

Two API routes exist and work end-to-end: POST /integrations to create and validate a new Cloudflare integration, and POST /syncs to trigger a manual sync for an existing integration. The sync enqueues a Celery task. The task runs the connector and logs the result. Snapshot and diff logic are wired in later milestones. The goal here is the plumbing: credentials encrypted and stored, tasks enqueued and received.

Files to Create

    /backend/app/routers/integrations.py        POST /integrations, GET /integrations routes
    /backend/app/routers/syncs.py               POST /syncs, GET /syncs/{id} routes
    /backend/app/schemas/integration.py         Pydantic schemas for integration create and response
    /backend/app/schemas/sync.py                Pydantic schemas for sync trigger and response
    /backend/app/services/encryption.py         AES-GCM encrypt and decrypt helpers
    /backend/app/services/user_service.py       get-or-create user record from Clerk JWT
    /backend/app/workers/sync_tasks.py          sync_integration Celery task (stub for now)

Backend Tasks

    In encryption.py, implement encrypt(plaintext: str) -> tuple[bytes, bytes] and decrypt(ciphertext: bytes, iv: bytes) -> str using AES-GCM with the ENCRYPTION_KEY from config. The key should be a 32-byte base64-encoded value from the environment. Store the IV alongside the ciphertext in the integrations table.
    In user_service.py, implement get_or_create_user(clerk_id: str, email: str, display_name: str, db: Session) -> User. If a user with that clerk_id exists, return it. If not, create and return a new User row.
    In integrations.py:
        Implement POST /integrations. Accept a JSON body with provider (must be cloudflare), display_name, api_token, and zone_id. Call validate_token from the Cloudflare connector. If validation fails, return HTTP 400 with the error message. If validation succeeds, encrypt the credentials (serialize api_token and zone_id to JSON, then encrypt), create the Integration row, create a Resource row with provider_resource_type cloudflare_dns_zone and provider_resource_id equal to the zone_id. Return the created integration ID and status.
        Implement GET /integrations. Return a list of all integrations for the authenticated user, including id, provider, display_name, status, and last_synced_at.
    In syncs.py:
        Implement POST /syncs. Accept a JSON body with integration_id. Verify the integration belongs to the authenticated user. Create a SyncRun row with status pending and triggered_by manual. Enqueue a sync_integration Celery task with the sync_run_id and integration_id. Return the sync_run_id.
        Implement GET /syncs/{id}. Return the SyncRun record by ID, scoped to the authenticated user, with status, started_at, completed_at, change_count, and error_message.
    In sync_tasks.py, write a stub sync_integration Celery task that accepts sync_run_id and integration_id, loads the integration from the database, decrypts credentials, calls the Cloudflare connector's fetch method, logs the number of records returned, and updates the SyncRun status to completed. No snapshot or diff logic yet.

Test Criteria

    POST /integrations with valid Cloudflare credentials creates an Integration row and a Resource row in the database.
    POST /integrations with an invalid API token returns HTTP 400 with a descriptive error message and does not create any database rows.
    POST /syncs enqueues a Celery task and returns a sync_run_id.
    The Celery worker picks up the task, loads credentials, calls the Cloudflare connector, and logs the record count.
    GET /syncs/{id} returns the correct status for the sync run.
    Credentials stored in the integrations table are ciphertext, not plaintext.

Definition of Done

An engineer can use the API to connect a Cloudflare account and trigger a sync. The sync task runs in the background and successfully calls the Cloudflare API using the stored credentials. The sync run record reflects the outcome. No snapshots are stored yet.


MILESTONE 8: SNAPSHOT SERVICE

Goal

The snapshot service accepts normalized DNS state from the Cloudflare connector, computes a SHA-256 content hash, compares it to the most recent snapshot for the resource, and writes a new Snapshot row only if the state has changed. The sync task is updated to call the snapshot service after fetching DNS records.

Files to Create

    /backend/app/services/snapshot_service.py   snapshot creation and deduplication logic

Backend Tasks

    In snapshot_service.py, implement store_snapshot(resource_id, integration_id, user_id, state: list[dict], triggered_by: str, sync_run_id, db: Session) -> tuple[Snapshot | None, bool].
        Compute a SHA-256 hash: sort the state list by record_id for determinism, serialize to canonical JSON (sorted keys, no extra whitespace), hash with hashlib.sha256.
        Query the most recent snapshot for the given resource_id ordered by created_at DESC. If a snapshot exists and its content_hash matches the new hash, return (None, False) indicating no change.
        If no existing snapshot exists, or the hash differs, create a new Snapshot row with state as JSONB, the content_hash, triggered_by, and sync_run_id. Commit and return (snapshot, True).
    Update the sync_integration Celery task in sync_tasks.py to call store_snapshot after fetching DNS records. Log whether a new snapshot was written or skipped.
    Update the SyncRun record's snapshot_count field to reflect how many new snapshots were written.

Test Criteria

    Calling store_snapshot with fresh DNS state creates a new Snapshot row in the database.
    Calling store_snapshot again with identical state returns (None, False) and writes no new row.
    Calling store_snapshot with slightly different state (one record modified) returns a new Snapshot.
    The content_hash stored on the Snapshot row matches the SHA-256 of the canonical serialization of the state.
    The sync task correctly updates snapshot_count on the SyncRun.

Definition of Done

After a sync runs, a Snapshot row exists in the database containing the full normalized DNS state. A second sync with no DNS changes produces no new snapshot. A second sync after a DNS record change produces a new snapshot. The snapshot is the permanent, immutable record of configuration state at a point in time.


MILESTONE 9: DIFF SERVICE

Goal

The diff service takes two consecutive snapshots for a resource, compares them record by record, identifies additions, deletions, and field-level modifications, and writes Change rows to the database. The sync task is updated to run the diff service after every snapshot write.

Files to Create

    /backend/app/services/diff_service.py       snapshot comparison and change record creation

Backend Tasks

    In diff_service.py, implement compute_diff(prev_snapshot: Snapshot, new_snapshot: Snapshot, resource_id, integration_id, user_id, db: Session) -> list[Change].
        Parse prev_snapshot.state and new_snapshot.state as lists of record dicts.
        Build a keyed index from each list using record_id as the key.
        Identify additions: record_ids present in new_snapshot but not in prev_snapshot. For each addition, create a Change row with change_type added, record_identifier set to a human-readable label (e.g., "A record: api.example.com"), prev_value null, new_value the full record dict as JSONB, risk_level pending (to be set by risk service), field_path null.
        Identify deletions: record_ids present in prev_snapshot but not in new_snapshot. For each deletion, create a Change row with change_type removed, prev_value the full record dict, new_value null.
        Identify modifications: record_ids present in both where field values differ. Compare these fields: record_type, name, content, ttl, proxied, priority, comment. For each field that differs, create one Change row with change_type modified, field_path set to the field name, prev_value and new_value as the specific field values wrapped in JSONB.
        Write all Change rows in a single database transaction. Return the list of Change objects.
    Update the sync_integration Celery task to call compute_diff after store_snapshot when a new snapshot was written. Pass the previous snapshot (the second most recent for the resource) and the new snapshot.
    Update the SyncRun record's change_count to reflect how many Change rows were written.

Test Criteria

    Given two snapshots with identical state, compute_diff returns an empty list and writes no Change rows.
    Given a snapshot where one A record is new, compute_diff returns one Change with change_type added.
    Given a snapshot where one record is missing compared to the previous, compute_diff returns one Change with change_type removed.
    Given a snapshot where a record's content field changed, compute_diff returns one Change with change_type modified and field_path content and the correct prev_value and new_value.
    Given a snapshot where two fields on the same record changed, compute_diff returns two Change rows for that record.
    All Change rows reference the correct prev_snapshot_id and new_snapshot_id.

Definition of Done

After two syncs where at least one DNS change occurred between them, the changes table contains accurate Change rows describing every field-level difference. The change_count on the SyncRun is correct. If no changes occurred between syncs, the changes table gains no new rows.


MILESTONE 10: RISK CLASSIFICATION SERVICE

Goal

The risk service reads Change rows produced by the diff service and assigns a risk level (low, medium, high, or critical) and a plain-English risk_reason to each one. Risk rules are stored as code in a dedicated module. The sync task is updated to call the risk service after the diff service.

Files to Create

    /backend/app/services/risk_service.py               risk classification logic and rule application
    /backend/app/services/risk_rules/cloudflare.py      Cloudflare DNS risk rules

Backend Tasks

    In risk_rules/cloudflare.py, define the rule set as a function classify_cloudflare_change(change: Change) -> tuple[str, str] that returns a (risk_level, risk_reason) pair based on the following logic:
        Critical: change_type is removed and the record being deleted is an A, AAAA, or CNAME at a root or apex domain (no subdomain prefix). Critical: change_type is removed and the record is type MX. Critical: change_type is modified, field_path is record_type and the type is NS or SOA.
        High: change_type is removed for any record type not already classified as critical. High: change_type is modified, field_path is content, and the record type is CNAME or MX. High: change_type is modified, field_path is proxied, and prev_value is true and new_value is false (proxy disabled). High: change_type is modified, field_path is ttl, and new_value is 60 or below.
        Medium: change_type is modified, field_path is proxied, and prev_value is false and new_value is true (proxy enabled). Medium: change_type is modified and field_path is ttl and new_value is above 60 (general TTL change). Medium: change_type is modified and field_path is content and record type is TXT. Medium: change_type is added and record type is A or AAAA and the name contains a subdomain.
        Low: change_type is modified and field_path is comment. Low: any change that does not match a higher rule.
        Each risk reason should be a one to two sentence plain English explanation of why the risk level was assigned. For example: "Disabling Cloudflare proxy removes DDoS protection and exposes the origin IP address directly to the internet."
    In risk_service.py, implement classify_changes(changes: list[Change], db: Session) -> None.
        For each Change in the list, call the appropriate provider rule function based on the integration's provider type. In the MVP, all changes go through classify_cloudflare_change.
        Update each Change row with the returned risk_level and risk_reason.
        Commit all updates in a single transaction.
    Update the sync_integration Celery task to call classify_changes immediately after compute_diff.

Test Criteria

    A Change with change_type removed for an A record at the apex domain (name equals the bare zone, e.g., example.com) is assigned risk_level critical.
    A Change with change_type removed for any MX record is assigned risk_level critical.
    A Change with change_type modified, field_path ttl, and new_value 60 is assigned risk_level high.
    A Change with change_type modified, field_path ttl, and new_value 61 is assigned risk_level medium.
    A Change with change_type modified, field_path comment is assigned risk_level low.
    A Change with change_type modified, field_path proxied, prev_value true, new_value false is assigned risk_level high.
    Each Change row has a non-null risk_reason after classification.

Definition of Done

After a full sync that detected changes, every Change row in the database has a risk_level of low, medium, high, or critical, and a non-null risk_reason in plain English. The risk levels match the rules defined in this milestone. No change is left with a null or pending risk level after the sync task completes.


MILESTONE 11: CHANGES API

Goal

Three read API routes are implemented that power the frontend timeline and change detail views: GET /changes for the paginated timeline, GET /changes/{id} for a single change detail, and GET /resources/{id}/changes for resource-scoped change history. These routes read from the changes and snapshots tables and return clean, typed JSON responses.

Files to Create

    /backend/app/routers/changes.py             GET /changes, GET /changes/{id}

Backend Tasks

    In changes.py, implement GET /changes with query parameters: integration_id (optional UUID), risk_level (optional string), resource_id (optional UUID), limit (default 50, max 200), offset (default 0). Return a list of ChangeResponse objects ordered by created_at DESC, scoped to the authenticated user. Each ChangeResponse includes: id, resource_id, integration_id, change_type, record_identifier, field_path, prev_value, new_value, risk_level, risk_reason, created_at, and the resource's display_name and the integration's display_name via joins.
    In changes.py, implement GET /changes/{id}. Return a ChangeDetailResponse that includes all ChangeResponse fields plus the full prev_snapshot state and new_snapshot state as JSON, and both snapshot created_at timestamps.
    In resources.py, implement GET /resources/{id} returning resource metadata: id, provider_resource_type, display_name, last_snapshot_at, integration_id, and the integration's provider and display_name.
    In resources.py, implement GET /resources/{id}/changes with limit and offset parameters, returning the same ChangeResponse shape filtered by resource_id.
    In resources.py, implement GET /resources/{id}/snapshots with limit and offset parameters. Return a list of SnapshotSummaryResponse objects: id, content_hash, triggered_by, created_at, and a change_count computed by counting Change rows with new_snapshot_id equal to this snapshot's id.
    All routes must be scoped to the authenticated user via the get_current_user dependency. A user cannot read resources or changes that belong to another user.
