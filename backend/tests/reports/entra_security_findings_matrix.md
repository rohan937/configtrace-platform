## Deliberately rejected / deferred candidates (GAP rows)

| Candidate | Reason | Status |
|---|---|---|
| Role-assignable group without an actual role assignment | Eligibility alone is not privilege; only an actual role assignment (rules 1-4, 9-10) is Finding-worthy. | GAP (rejected) |
| Every Guest user / every multi-tenant app / every unverified-publisher app / every delegated consent / every app assignment / every disabled user (alone) | Normal inventory in most tenants; only risky combinations are implemented. | GAP (rejected) |
| No FIDO2/phishing-resistant authenticator configured (tenant-wide absence) | Requires `entra_organization.family_completeness` visibility the per-record evaluator interface doesn't have; would need a connector-side rollup record (deferred to a future message). | GAP (deferred) |
| No legacy-auth block found (tenant-wide absence) | Same reasoning — absence-based claims require known-complete collection this evaluator can't verify per-record. | GAP (deferred) |
| Conditional Access policy requires a non-phishing-resistant authentication strength | Genuine cross-record join (CA policy -> authentication_strength via `authentication_strength_id`) the per-record evaluator can't perform; `entra_authentication_strength_not_phishing_resistant` (rule 36) is a weaker, single-record proxy instead. | GAP (deferred) |
| Temporary Access Pass lifetime/one-time-use thresholds | `entra_authentication_method` does not carry TAP-specific lifetime/one-time-use fields this message; no documented threshold to invent. | GAP (deferred, schema extension needed) |
| FIDO2 disabled (absence rule) | Presence-based Findings are preferred over absence-based ones; disabling one method is not evidence of overall MFA loss. | GAP (rejected) |
| Requested (not granted) high-risk permission | `requiredResourceAccess` is requested/configured, never granted; message 3's own docstring already established this must never be conflated with an actual grant. | GAP (rejected) |
| offline_access alone | Never a Finding by itself; only contextual evidence inside the broader consent-risk rules (never tiered above "low"). | GAP (rejected) |
| Multi-tenant app registration alone | Requires the same kind of cross-record join (app -> permission/consent context) as the CA/auth-strength case; deferred for identical reasons. | GAP (deferred) |
| Privileged service principal + password credential exists (mere presence) | Client secrets are a normal, common credential type; flagging mere presence would be noise. Credential-EXPIRY rules (40, 41) implemented instead. | GAP (rejected) |
| Guest assigned to an enterprise application (generic) | Ordinary inventory in most tenants; no deterministic single-record signal that the application itself is high-privilege. | GAP (rejected) |

## Parity / architecture confirmations

* **Registry parity**: `KNOWN_RULE_KEYS` contains exactly these 45 `entra_*` keys — `tests/test_entra_security_finding_parity.py::TestRegistryParity`.
* **Confidence parity**: every rule has a `RULE_CONFIDENCE` entry (high or medium, never low) with a non-empty false-positive guard — `TestConfidenceParity`.
* **Pack parity**: every rule has a `_RULE_META` entry with provider="entra", a valid severity, and a category drawn from the 8-category vocabulary above — `TestPackParity`.
* **Evaluator parity**: `entra_rules.evaluate` is registered in `_PROVIDER_RULES["entra"]` — `TestModuleDispatchReachable`.
* **Coverage groundwork parity**: every rule has a `RULE_RECORD_TYPES` entry (groundwork for message 8), but `"entra"` is deliberately absent from `security_coverage_service.PROVIDERS` / `PROVIDER_SURFACES` — `TestCoverageParity`.
* **Frontend parity**: every rule appears in `frontend/src/lib/securityRuleCatalog.ts` with matching severity — `TestFrontendParity`. `npx tsc --noEmit` passes with zero errors.
* **Full cross-layer parity**: module/registry/confidence/pack/coverage/frontend key sets are identical, and the rule count is pinned at 45 — `TestFullCrossLayerParity`.
* **Finding-vs-Change severity parity**: for the 9 representative high-value rules covering Global Admin, PRA, high-tier admin, group-grants-Global-Admin, guest Global Admin, critical SP permission, tenant-wide high-risk consent, no-MFA CA, and wildcard redirect — Change severity is always >= static Finding severity. One real mismatch was found and fixed during this message: `risk_rules/entra.py`'s `_classify_sp_app_role_assignment_change()`'s "added" branch did not consult the message-5 `app_role_privilege_tier` field, capping newly-granted critical-tier Graph permissions (e.g. `RoleManagement.ReadWrite.Directory`) at "high" — it now escalates to "critical" when `app_role_privilege_tier` is explicitly critical, matching the new `entra_service_principal_can_manage_directory_roles` Finding's severity — `TestFindingVsChangeSeverityParity`.
* **Connector-shape reachability**: at least one rule per category is proven reachable through the REAL connector normalize/derive functions (never hand-fabricated Finding dicts), including the required cross-record derivation paths (user+role-assignment -> privileged identity; group+role-assignment+membership -> privileged group AND inherited user privilege; SP+critical Graph permission grant -> privileged service principal) — `tests/test_entra_security_findings_reachability.py`, 11 tests, all PASS.
