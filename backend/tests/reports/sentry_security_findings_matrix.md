## Deliberately rejected/deferred rules

- **Repository/code-mapping cross-record joins** (`sentry_repository_uses_disabled_integration`, `sentry_repository_missing_integration`, `sentry_code_mapping_missing_repository`, `sentry_code_mapping_missing_project`): the Finding evaluator's interface is `evaluate(record) -> list[FindingCandidate]`, one record at a time, with no access to sibling records. Repositories and code mappings were never given a connector-side denormalized join (unlike alert actions, which message 5 already joined onto `sentry_routing_context.integration_status_category`). Adding one is a connector-schema change, out of this message's Findings-only scope.
- **`sentry_alert_references_missing_integration`**: `integration_status_category` is `None` for both "no integration target" and "integration_id unresolved" — the derived record cannot distinguish them. Only the confirmed case (integration resolved AND explicitly disabled) is implemented.
- **`sentry_ownership_rule_invalid`**: the Sentry API exposes no deterministic per-rule validity flag, and current docs confirm the API refuses to save a rule with an unresolved owner in the first place — "invalid" is not an observable state.
- **`sentry_project_ownership_unroutable`** / **`sentry_project_has_no_ownership_rules`**: genuine cross-record aggregates (every target for one project unresolved / per-project family-completeness absence) that the per-record evaluator cannot compute without a connector-side rollup, mirroring the Okta message-6 precedent for deferred tenant-wide aggregates.
- **Billing-role privileged-member Finding**: current docs establish no project/team/integration authority for Billing beyond payment/compliance visibility.
- **Standalone disabled-integration Finding**: a disabled integration with nothing depending on it is not itself a live risk; only the referenced-and-disabled combination is implemented.
- **Threshold-weakening / environment-coverage static Findings**: these are Change-classification concerns (already covered by `risk_rules/sentry.py`), not application-independent static posture.
- **Multiple valid alert actions**: redundant routing is generally positive, not risky — no Finding.
- **Separate pending-vs-inactive-member rules**: the derived `sentry_routing_context`/`sentry_privileged_member` records cannot distinguish a pending member from an expired one — both surface identically as `target_active=False` — so a single merged rule is used instead of inventing a distinction the data doesn't support.
